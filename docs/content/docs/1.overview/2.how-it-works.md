---
title: How Nuxt Photo works
description: The photo model, collection ownership, recipes, image pipeline, and lightbox runtime in one mental model.
---

Nuxt Photo has a few supported entry points. They are ordered by how much UI and
lightbox behavior you own. Stay on the highest layer that solves the current
problem.

```text
<PhotoAlbum> / <Photo> / <PhotoCarousel>  Ready-made gallery pieces
<PhotoGroup>                              Shared lightbox across photos/albums
<LightboxProvider> + <PhotoTrigger>       Custom layout, default lightbox
Recipe <Lightbox> slots                   Custom lightbox regions
Primitives + composables                  Custom lightbox structure
```

## The ladder

| Step                      | Learn this                       | Unlocks                                      | Stop here when                                      |
| ------------------------- | -------------------------------- | -------------------------------------------- | --------------------------------------------------- |
| Recipe components         | `photos`, layout, shallow props  | Albums, single photos, carousels, lightbox   | Rows/columns/masonry/carousel match the design      |
| `<PhotoGroup>`            | Shared lightbox scope            | One viewer across many photos or albums      | Built-in layouts still work                         |
| Explicit primitives       | Provider and trigger composition | Any thumbnail layout, default lightbox       | The lightbox UI is still acceptable                 |
| Recipe `<Lightbox>` slots | Caption/actions/slide slots      | Branded lightbox chrome without new runtime  | The default lightbox structure is still acceptable  |
| Primitives + composables  | Provider context and nesting     | Custom overlay, viewport, controls, gestures | You need a different lightbox structure or behavior |

## Recipe components

Use recipe components first. They cover the common cases: a single photo, an
album, a grouped set of albums, or a carousel.

```vue
<PhotoAlbum :photos="photos" layout="rows" />
```

Use recipes when:

- You want a gallery without owning lightbox internals.
- Rows, columns, masonry, or carousel match the design.
- CSS variables, classes, and slots are enough customization.

Rows are the most forgiving SSR path. Tune `defaultContainerWidth` and
`breakpoints` later only when the gallery is above the fold and CLS matters.

## Grouping and custom layouts

Use `<PhotoGroup>` when several photos or albums should share one lightbox and one next/previous flow.

```vue
<PhotoGroup :photos="[...landscapes, ...studies]">
  <PhotoAlbum :photos="landscapes" layout="rows" />
  <PhotoAlbum :photos="studies" layout="columns" />
</PhotoGroup>
```

Use explicit primitives when the built-in layout is wrong but the default lightbox is still right.

```vue [app/components/CustomThumbnailLayout.vue]
<script setup lang="ts">
import {
  Lightbox,
  LightboxProvider,
  PhotoImage,
  PhotoTrigger,
  type PhotoItem,
} from '@lupinum/nuxt-photo/app'

defineProps<{ photos: readonly PhotoItem[] }>()
</script>

<template>
  <LightboxProvider :photos="photos">
    <PhotoTrigger v-for="(photo, i) in photos" :key="photo.id" :photo="photo" :index="i">
      <PhotoImage :photo="photo" context="thumb" />
    </PhotoTrigger>
    <Lightbox />
  </LightboxProvider>
</template>
```

## Lightbox slots

Use the recipe `<Lightbox>` slots when the built-in viewer behavior is right but
the visible UI is not. This is the shallow path for changing captions, counters,
action buttons, or slide markup.

```vue
<script setup lang="ts">
import { Lightbox } from '@lupinum/nuxt-photo/app'
</script>

<template>
  <Lightbox>
    <template #caption="{ photo }">
      <div class="my-caption">
        <h2>{{ photo?.caption }}</h2>
        <p>{{ photo?.description }}</p>
      </div>
    </template>
  </Lightbox>
</template>
```

Pass that wrapper through `:lightbox` on a recipe component, or provide it
globally with `LightboxComponentKey`.

## Custom lightboxes

Use primitives and `provideLightbox()` when you need a different lightbox structure. The primitives provide context wiring, focus handling, viewport bindings, controls, captions, slide rendering, and the internal FLIP transition layer. You still own the markup, classes, and final accessibility review for your composition.

```vue [app/components/CustomLightbox.vue]
<script setup lang="ts">
import {
  LightboxCaption,
  LightboxControls,
  LightboxOverlay,
  LightboxProvider,
  LightboxRoot,
  LightboxSlide,
  LightboxViewport,
  PhotoImage,
  PhotoTrigger,
  type PhotoItem,
} from '@lupinum/nuxt-photo/app'

defineProps<{ photos: readonly PhotoItem[] }>()
</script>

<template>
  <LightboxProvider :photos="photos">
    <PhotoTrigger v-for="(photo, i) in photos" :key="photo.id" :photo="photo" :index="i">
      <PhotoImage :photo="photo" context="thumb" />
    </PhotoTrigger>

    <LightboxRoot role="dialog" aria-modal="true" aria-label="Photo viewer">
      <LightboxOverlay />
      <LightboxViewport v-slot="{ photos, viewportRef }">
        <div :ref="viewportRef" class="embla">
          <div class="embla__container">
            <LightboxSlide v-for="(photo, i) in photos" :key="photo.id" :photo="photo" :index="i" />
          </div>
        </div>
      </LightboxViewport>
      <LightboxControls />
      <LightboxCaption />
    </LightboxRoot>
  </LightboxProvider>
</template>
```

Reach for this only when recipe slots and CSS are not enough.

## Picking an entry point

| Need                               | Entry point                      |
| ---------------------------------- | -------------------------------- |
| A normal gallery or carousel       | Recipes                          |
| One lightbox across several albums | `<PhotoGroup>`                   |
| Custom thumbnail layout            | Explicit primitives              |
| Custom captions/actions/slides     | Recipe `<Lightbox>` slots        |
| Custom lightbox DOM or controls    | Primitives + `provideLightbox()` |

Most projects should stay on recipes or grouping.
