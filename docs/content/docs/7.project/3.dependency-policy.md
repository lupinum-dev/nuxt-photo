---
title: Runtime dependency policy
description: How Nuxt Photo contains runtime dependency risk.
---

Runtime dependencies need one clear owner and must not leak into core photo,
layout, validation, or lightbox domain logic.

## Embla carousel

`PhotoCarousel` uses Embla 9 for motion and drag mechanics. Embla 9 is currently
published as a release candidate; the project accepts that explicitly for this
greenfield release and pins the exact version instead of using a range.

The boundary is intentionally narrow:

- Recipe carousel orchestration lives in
  `components/photo-carousel/usePhotoCarouselRuntime.ts`.
- `integrations/embla/snapModel.ts` is the single exact-version boundary allowed
  to read Embla's private slide-to-snap registry.
- Public component props use `PhotoCarouselOptions` and
  `PhotoCarouselAutoplayOptions`, never Embla types or plugin objects.
- No other production file calls `internalEngine()`.

Before changing the pinned Embla version, run the carousel unit tests and verify
looping, grouped slides, navigation, selection after `reInit`, autoplay, and
lightbox activation in the playground. Review the generated declarations to
ensure vendor types still do not enter the public API.

## Adding dependencies

Add a runtime dependency only when it replaces complexity the library would
otherwise own. Keep its boundary narrow, pin unstable versions exactly, and add
an integration test that fails when the used public contract changes.
