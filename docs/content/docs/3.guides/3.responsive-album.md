---
title: Tune a responsive album
description: Choose layout values from the gallery container and keep SSR assumptions aligned.
---

Start from the container widths where the composition stops working, not from
a device list. `responsive()` selects the value for the largest matching
minimum width.

```vue [app/components/PortfolioAlbum.vue]
<script setup lang="ts">
const columns = responsive({ 0: 2, 640: 3, 960: 4, 1280: 5 })
const spacing = responsive({ 0: 4, 640: 8, 960: 12 })
</script>

<template>
  <PhotoAlbum
    :photos="photos"
    :layout="{ type: 'columns', columns }"
    :spacing="spacing"
    :breakpoints="[640, 960, 1280]"
    :default-container-width="960"
  />
</template>
```

The album measures its own container, so the same component can sit in a full
page, sidebar, or split layout without reading the viewport. Explicit
`breakpoints` replace inferred breakpoint metadata; keep the list aligned with
the keys used by `responsive()`.

## Tune one variable at a time

- For `rows`, raise `targetRowHeight` when the gallery should show fewer,
  larger photos.
- For `columns` and `masonry`, increase `columns` as the container grows.
- Keep `spacing` small enough that the images still read as one collection.
- Use `padding` only when each item needs an internal frame.

A function can produce smooth scaling when breakpoint jumps are visible:

```vue [app/components/PortfolioAlbum.vue]
<PhotoAlbum
  :photos="photos"
  :spacing="(width) => Math.round(Math.max(4, Math.min(16, width / 80)))"
/>
```

Functions carry no inferred breakpoint metadata. Add explicit `breakpoints`
when measurement should snap, and choose a realistic
`defaultContainerWidth` for server rendering. The [server rendering concept]($docs/concepts/server-rendering)
shows when these assumptions improve the initial geometry and when they can
still differ after hydration.
