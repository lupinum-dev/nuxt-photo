---
title: Intentional sharp edges
description: Behaviors that are intentional but easy to misuse.
---

Nuxt Photo tries to fail loudly at public boundaries, but a few choices still
matter for correctness and maintainability.

## Photo data

Every photo needs a stable `id`, `src`, `width`, and `height`. Duplicate ids are
invalid. Recipe components validate photo lists before layout math runs, and the
default policy is `validation="throw"`.

Use `validation="drop"` only when losing invalid photos is acceptable and you
handle `onInvalidPhotos`. Silent data loss should not be the default for CMS or
API regressions.

## PhotoGroup ownership

`<PhotoGroup>` receives one explicit `photos` collection. That collection owns
identity and navigation order; descendant `<Photo>` and `<PhotoAlbum>` recipes
only contribute thumbnail elements and optional custom slide renderers.

```vue
<PhotoGroup :photos="[...landscapes, ...studies]">
  <PhotoAlbum :photos="landscapes" />
  <PhotoAlbum :photos="studies" />
</PhotoGroup>
```

A group mounted with `lightbox=false` is inert. It does not create a provider
later if the prop changes. Mount a new enabled group when you need a provider.

## CSS

`css: 'structure'` is the minimum viable module setting. `css: 'none'` means you
own every structural class needed for album layout, carousel layout, lightbox
positioning, focus behavior, and transitions.

## Custom adapters and lightboxes

Custom image adapters should be deterministic for SSR. The same photo and
context should produce the same result on server and client.

Custom lightbox components should consume the provider created by Nuxt Photo.
Do not create a second provider inside the custom lightbox unless you are
intentionally replacing the full state model.

## Carousel

`PhotoCarousel` exposes only library-owned options. Actual snap groups are
geometry-dependent and come from the pinned Embla runtime through
`packages/vue/src/integrations/embla/snapModel.ts`. Run the real-geometry
integration tests before changing the Embla version, containment, slide sizing,
or grouping behavior.

## One active lightbox

Only one provider owns modal focus and page isolation at a time. Opening another
lightbox first closes the current owner. This prevents competing focus traps,
inert page state, and ambiguous keyboard ownership.
