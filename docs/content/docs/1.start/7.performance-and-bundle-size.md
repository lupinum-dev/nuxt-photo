On a photo page the images cost far more than the script. Get image delivery
right first, then check which components you ship.

## Keep image cost low

- Store the real `width` and `height`, so the browser reserves space before
  each image loads.
- Serve resized files: use Nuxt Image, or `srcset` candidates you prepare.
- Set `sizes` to the width the thumbnail really takes, so the browser does not
  pick a file that is larger than needed.
- Use `thumbSrc` when you have a separate small file for thumbnails.
- Keep images below the first screen lazy (the default).

[Deliver images](/docs/guides/deliver-images) covers each option.

## What loads before interaction

A page with `Photo`, `PhotoAlbum`, `PhotoCarousel` or `PhotoGroup` loads the
thumbnails, their layout CSS and the code that renders them. The viewer (the
lightbox, its gestures, zoom, transitions, its CSS and the labels only the
viewer shows) is a separate chunk. It loads at the first of these:

- the first pointer, touch or keyboard focus on a photo;
- an idle moment after the first photo becomes visible, unless the browser
  asks to save data (`navigator.connection.saveData`);
- a request to open a photo: a click, `Enter`, `open()`, `openById()` or the
  `active` prop.

A page that the server renders with a deep link to an open photo includes the
viewer and its CSS at once. A group with `lightbox: false` never loads the
viewer.

On a slow network, the first open of a photo waits for the viewer chunk and its
CSS. Usually a pointer or focus starts the download before the click.

## Bundle size

Production builds, Brotli-compressed, measured with the repository's
`pnpm size` check on 15 November 2026. Nuxt rows are the difference from the
same empty Nuxt app.

| What the app uses                                     | Brotli      |
| ----------------------------------------------------- | ----------- |
| Nuxt module enabled, no photo component rendered      | `+1,927 B`  |
| Nuxt module with one `PhotoImage`                     | `+1,977 B`  |
| Nuxt module with one `PhotoAlbum`, before interaction | `+19,477 B` |
| Nuxt module with one `PhotoAlbum`, viewer included    | `+40,362 B` |
| Vue: `responsive` only                                | `657 B`     |
| Vue: `useLightbox` only                               | `533 B`     |
| Vue: `PhotoImage` only                                | `3,102 B`   |
| Vue: the complete package, viewer included            | `49,700 B`  |

The `PhotoAlbum` rows are the numbers to compare with other gallery libraries:
the first is what the page needs to show the album, the second adds the
complete lightbox. Nuxt auto-imports add only the components a page renders.

Measure your own app too. Other modules, route splitting, CSS, and image formats
change what users download.

## Masonry with many photos

Albums get their positions from CSS that the server renders into the page. For
`rows` and `columns` this CSS stays small. A `masonry` album with a responsive
column count writes one rule set per column count, and each set places every
photo.

| Masonry album with 1,000 photos        | CSS in the page                         |
| -------------------------------------- | --------------------------------------- |
| Fixed column count, such as `3`        | 208 B, plus about 42 B inline per photo |
| Responsive count of 2, 3 and 4 columns | 141,201 B raw, 32,691 B gzip            |

The CSS grows with the number of photos times the number of column counts. For
a masonry album with several hundred photos, use a fixed column count, use
fewer column counts, or show the photos in pages.
