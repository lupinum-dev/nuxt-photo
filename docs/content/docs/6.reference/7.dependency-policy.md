---
title: Dependency policy
description: How Nuxt Photo treats runtime dependency risk.
---

Nuxt Photo keeps runtime dependencies small and contained. A dependency should
have one clear owner in the source tree, and framework or vendor-specific
behavior should not leak into core photo, layout, validation, or lightbox domain
logic.

## Embla carousel

`PhotoCarousel` uses Embla for carousel mechanics. Embla integration lives in the
carousel recipe and `packages/vue/src/integrations/embla`. No core module should
import Embla.

One helper, `readEmblaSnapStateUnsafe`, reads Embla private snap grouping from
`api.internalEngine().scrollSnapList.{slidesBySnap,snapBySlide}`. The carousel
needs that grouping so dots, thumbnails, counters, and lightbox slide activation
stay aligned when `slidesToScroll` groups more than one photo.

If that private shape is missing or unusable, Nuxt Photo falls back to
deterministic `slidesToScroll` chunks. That fallback keeps the carousel usable,
but it may not match every Embla edge case as precisely as the real snap state.

Before upgrading Embla:

1. Read `packages/vue/src/integrations/embla/snapState.ts`.
2. Run `pnpm exec vitest run packages/vue/test/recipes/emblaSnapState.test.ts packages/vue/test/recipes/carousel.test.ts`.
3. Verify canary coverage for `slidesToScroll: 1`, `slidesToScroll: 2`,
   `loop: true`, photo counts smaller than the slide group, and `reInit`.
4. Keep private Embla reads in the integration file. Do not read
   `internalEngine()` from components, composables, core modules, or tests except
   through the canary helper tests.

## Adding dependencies

Add a runtime dependency only when it replaces real complexity that the library
would otherwise have to own. Keep the dependency boundary narrow, document any
private or unstable API use, and add focused tests that fail on upgrade
regressions.
