---
title: How Nuxt Photo works
description: Understand the photo model, recipe components, providers, and customization boundary.
---

Nuxt Photo separates photo data from the way that data is laid out, delivered, and opened. Every built-in experience starts with the same `PhotoItem` collection and adds only the behavior it owns.

```text [Architecture]
PhotoItem[]
    |
    +-- recipe component ---- layout and triggers
    +-- image adapter ------- final image attributes
    +-- lightbox provider --- navigation, zoom, gestures, and focus
```

## Start with a recipe component

Recipe components cover the common paths without exposing the underlying state model.

| Component         | Use it for                                                  | Lightbox default |
| ----------------- | ----------------------------------------------------------- | ---------------- |
| `<Photo>`         | One figure, with an optional solo viewer                    | Off              |
| `<PhotoAlbum>`    | Rows, columns, or masonry                                   | On               |
| `<PhotoGroup>`    | One viewer shared by several descendant recipes             | On               |
| `<PhotoCarousel>` | A horizontal carousel with optional thumbnails and controls | Off              |

`PhotoAlbum` is the usual starting point. It validates the collection, calculates the selected layout, renders image triggers, and creates its own lightbox provider.

```vue [app/pages/gallery.vue]
<template>
  <PhotoAlbum :photos="photos" layout="rows" />
</template>
```

The [component reference]($docs/components/photo-album) lists the props and slots when the default recipe already matches the intended structure.

## Share a collection deliberately

Each standalone recipe with a lightbox enabled owns its own viewer. Wrap related recipes in `PhotoGroup` when they should navigate through one ordered collection instead.

```vue [app/pages/portfolio.vue]
<template>
  <PhotoGroup :photos="allPhotos">
    <PhotoAlbum :photos="landscapes" />
    <PhotoAlbum :photos="portraits" />
  </PhotoGroup>
</template>
```

The group collection is canonical. Descendant order can change without changing the lightbox order, and every descendant ID must exist in the group collection.

## Move down one layer at a time

Use the narrowest customization surface that produces the required result:

1. Change recipe props for layout, behavior, and classes.
2. Replace a recipe slot for custom thumbnail, caption, control, or slide markup.
3. Combine `LightboxProvider`, `PhotoTrigger`, and the recipe `Lightbox` for a custom thumbnail layout.
4. Compose the lightbox primitives when the overlay, viewport, controls, or caption structure must change.

The lower layers preserve Nuxt Photo's state and interaction model, but they give the application more responsibility for markup, styling, and accessibility. The [custom thumbnail guide]($docs/customization/custom-thumbnail-layout) shows the provider boundary without rebuilding the viewer.

## Keep each setting at its owner

Module options choose app-wide registration, CSS, image delivery, and lightbox defaults. Recipe props configure one rendered experience. `PhotoItem` carries content data, while slots and primitives own custom markup.

Keeping those boundaries intact prevents duplicated providers, competing navigation order, and image behavior that differs between thumbnails and slides.
