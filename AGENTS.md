# Nuxt Photo agent guide

Own the result as a maintainer whose name is on the release. Prefer the
smallest correct system:

```text
delete > simplify > replace > add
```

Before adding infrastructure, configuration, a public export, compatibility
behavior, or generated state, identify the concrete problem and the acceptance
criterion.

## Sources of truth

- `package.json`: root commands, supported Node range, and pnpm version.
- `pnpm-workspace.yaml`: workspace membership, shared tool versions, dependency
  policy, and reviewed install scripts.
- `vite.config.ts`: Vite+ formatting, Oxlint, Vitest, and test aliases.
- `packages/vue/package.json`: the published Vue package contract.
- `packages/nuxt/package.json`: the published Nuxt module contract and its
  dependency on `@lupinum/vue-photo`.
- `packages/*/src/`: package implementation.
- `packages/*/test/`, `test/`, `playground`, and `playground-tailwind`: behavior,
  browser, package, and consumer contracts.
- `docs/`: the public documentation application and a real workspace consumer.
- `CONTRIBUTING.md`: contributor workflow.
- `MAINTAINING.md`: release, rollback, support, and repository settings.
- GitHub workflows: authoritative pull-request, main, versioning, security, and
  publication gates.
- Changesets: pending release intent for every user-visible package change.
- `packages/vue/CHANGELOG.md` and `packages/nuxt/CHANGELOG.md`: canonical
  package release histories, generated by Changesets during normal releases.
- `CHANGELOG.md`: index linking to the two package histories. It does not own
  release entries.

Do not repeat dependency or runtime versions in prose unless documenting
historical evidence. Read them from their manifest source.

## Daily workflow

Vite+ is the default developer interface.

After pulling dependency changes:

```sh
vp install
```

During ordinary work:

```sh
vp check
vp test
```

Before handoff:

```sh
pnpm verify
git status --short
```

Use the canonical repository gates when the change needs them:

```sh
pnpm docs:build
pnpm audit:all
pnpm release:verify
```

Useful focused commands:

```sh
vp test packages/vue/test/core/layout.test.ts
vp test packages/nuxt/test/module.test.ts
vp run typecheck
vp run test:browser
vp run build:docs
vp run release:pack
```

Use the narrowest useful command while iterating, then escalate once. Do not
repeatedly run the complete browser and release gates after every small edit.

## Nuxt and Vue Vite+ profile

Vite+ owns the common toolchain:

- Oxfmt for formatting;
- Oxlint for general JavaScript and TypeScript linting;
- type-aware Oxlint rules;
- Vitest execution;
- workspace task execution and package-manager delegation.

Nuxt Photo has three intentional framework-specific tools:

- `eslint-plugin-vue` checks Vue template semantics that Oxlint does not yet
  cover. It must stay limited to authored `.vue` files and must not become a
  second general JavaScript or TypeScript linter.
- `vue-tsc` is the authoritative TypeScript compiler check for Vue SFCs.
- Nuxt preparation and Nuxt Module Builder are authoritative for generated Nuxt
  aliases, module declarations, and application types.

The TypeScript compiler diagnostic path inside Oxlint/TS-Go is not authoritative
for this repository. It cannot presently model `.vue` imports, Nuxt-generated
`#app`/`#imports` aliases, or the complete workspace build graph without false
failures. Keep compiler verification in the explicit `typecheck` and Nuxt build
commands. Do not weaken or delete those commands because `vp check` is green.

Keep the repository on one Vite runtime. Do not install a separate real Vite
beside the Vite+ core alias. Nuxt's required Rolldown peer belongs in the
reviewed root toolchain rather than creating a second Vite path.

Keep `unbuild` for the Vue package's SFC-preserving distribution and
`nuxt-module-build` for the Nuxt module. Vite+ is the common interface, not a
reason to replace a framework-specific build that owns a real package contract.

Use `vp help` or the version-matched documentation in
`node_modules/vite-plus/docs` before guessing at Vite+ behavior.

## Test escalation

| Change                                        | First proof                                | Escalation                          |
| --------------------------------------------- | ------------------------------------------ | ----------------------------------- |
| Pure photo/layout helper                      | Targeted `vp test <file>`                  | `vp test`                           |
| Vue component, composable, or primitive       | Targeted Vue test                          | `vp run typecheck:packages`         |
| Nuxt module or runtime integration            | Targeted Nuxt test                         | `vp run build` and relevant fixture |
| Vue template markup                           | Targeted test and `pnpm lint:vue-template` | `pnpm verify`                       |
| Browser interaction or accessibility          | Focused Playwright project/file            | `vp run test:browser`               |
| Tailwind integration                          | Affected test or component check           | `vp run build:playground-tailwind`  |
| Public docs                                   | `vp run docs:validate`                     | `vp run build:docs`                 |
| Exports, dependencies, files, or declarations | `vp run release:pack`                      | packed clean consumer               |
| Release or workflow code                      | Focused script tests/checks                | `pnpm release:verify` on main CI    |

Fixture setup failure must fail the suite. Do not turn a required contract into
a skip merely because setup is inconvenient.

## Scope control

A branch owns one independently reviewable and revertible outcome. Tests,
documentation, and cleanup required to make that outcome correct belong on the
same branch.

When another idea appears, stop and classify it:

- Keep it on the branch when the original outcome would be wrong or incomplete
  without it.
- Split or defer it when it can ship independently, changes another public
  contract, or makes the pull-request summary require “and.”
- Record a useful follow-up instead of implementing it “while here.”
- Never discard unrelated work already present in the worktree.
- Do not rewrite reviewed history merely to make a branch look prettier.

If a branch has already grown too far:

1. Restate the intended outcome in one sentence.
2. List every independently releasable outcome now present.
3. Identify dependencies between those outcomes.
4. Make the smallest dependency-first outcome green and reviewable.
5. Propose follow-up branches in dependency order.
6. Move, revert, or rewrite existing work only with maintainer approval.
7. Tell the maintainer exactly what stayed, moved, and was deferred.

Use no arbitrary line-count, commit-count, or age limit. Optimize for one review
decision and one rollback decision.

Stay on the current branch. Do not create, switch, merge, rebase, push, or
rewrite branches unless the maintainer explicitly requests that Git operation.

## Public changes and Changesets

Add a Changeset for every user-visible change to either published package:

```sh
vp run changeset
```

The Changeset must name the affected package contract and explain user impact.
For a breaking change, include the migration action.

Do not:

- edit package versions by hand;
- maintain a second hand-written release-note path;
- add an empty Changeset merely to satisfy CI;
- omit a Changeset for a public change without explaining why the change has no
  published effect.

The two packages release as one coordinated set. Candidate creation and
publication must honor the Nuxt package's exact dependency on Vue. The
protected workflow publishes Vue before Nuxt.

## Release boundary

Before release work, read the Versioning, Publication, Partial failure, and
Rollback sections of `MAINTAINING.md`.

Agents may prepare code, tests, Changesets, release notes, and non-live
verification. Unless the maintainer explicitly authorizes the exact operation,
agents must not:

- dispatch the release workflow;
- approve a GitHub protected environment;
- publish a package;
- move or remove an npm dist-tag;
- create or overwrite a Git tag or GitHub Release;
- unpublish a version.

Never run `npm publish`, `pnpm publish`, or a local publication wrapper. The
supported release path consumes the retained exact-SHA package-set artifact from
main CI. Publication must not install dependencies, rebuild source, restore a
build cache, or create replacement tarballs.

## Release concierge

Natural-language requests such as “help me release this,” “ship this,”
“publish this,” or “what do I do next?” start the release concierge. They
authorize assessment and safe preparation, not publication.

The agent must:

1. Say immediately that assessment has started and nothing will be published
   without later exact approval.
2. Read the release and rollback sections of `MAINTAINING.md`.
3. Run `vp run release:notes`.
4. Inspect the worktree, Changesets, version pull request, current-main SHA,
   `Main healthy`, retained `release-candidate`, active release runs, dist-tags,
   provenance, tags, and GitHub Releases.
5. Use authoritative remote evidence instead of repeating a large local gate
   merely for reassurance.
6. List every known blocker, but recommend exactly one dependency-ordered next
   action.

Use this status shape:

```text
RELEASE STATUS: <BLOCKED | READY | AWAITING APPROVAL |
                 PUBLISHING | PARTIAL FAILURE | COMPLETE>

Package set:
- @lupinum/vue-photo@<version>
- @lupinum/nuxt-photo@<version>
Channel:
Source SHA:
CI run:
Artifact digests:

Confirmed:
- ...

Blocked:
- ...

Registry state:
- ...

Next action:
<exactly one recommended action>
```

Dispatching `.github/workflows/release.yml` requires explicit authorization tied
to:

- both package names and versions;
- intended channel;
- exact current-main SHA;
- automatically selected successful `ci` run ID;
- both retained tarball digests.

Dispatch the workflow with the exact fixed version. It selects the successful
current-main CI artifact. The protected `npm` environment then requires one
human approval. The isolated job publishes the certified Vue tarball before the
certified Nuxt tarball. It uses `next` for a prerelease and `latest` for a stable
release. It verifies registry bytes, provenance, and both dist-tags before it
creates the GitHub release.

Stay with the release until a terminal result. `COMPLETE` requires:

- both npm versions readable;
- provenance present for both, except for a documented first-version bootstrap
  whose registry bytes match the certified tarballs;
- final channel correct for both;
- Git tag present;
- one immutable GitHub Release present with durable evidence.

## Partial failure

Once npm accepts a version, it is immutable.

- Never rebuild or republish already-accepted bytes.
- Rerun the same workflow. It skips an existing version only when its SHA-1
  matches the certified tarball, then continues with the missing package.
- If registry state is ambiguous, stop and investigate one fact at a time.
- Rollback mutations require a new exact maintainer authorization.

## Security and package constraints

- Use a short branch name that describes the work, such as
  `fix/carousel-focus`. Do not require an agent or tool prefix such as
  `codex/`, `claude/`, or `cursor/`.
- Do not create a second release path.
- Do not publish from a local machine.
- Do not edit `dist`, `.release`, `.nuxt`, or `.output` by hand.
- Do not rely on hoisting, workspace source, or undeclared dependencies as
  consumer proof.
- Do not add Git, URL-tarball, local-tarball, `file:`, `link:`, `portal:`, or
  absolute-path dependencies.
- Do not add consumer lifecycle hooks without a documented contract and packed
  consumer proof.
- Update `allowBuilds` only after reviewing the dependency's install script.
- Keep browser coverage asymmetric: full Chromium behavior and focused
  cross-engine smoke unless a bug proves more is necessary.
- Use full commit SHAs for GitHub Actions.
- Preserve unrelated user changes in a dirty worktree.

Before finishing, verify that the change did not create a second source of
truth, leave obsolete code behind, broaden branch scope silently, weaken the
packed-consumer contract, or make release recovery harder.
